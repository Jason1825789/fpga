# 代码审查修改说明（2026-10-04）

本文件记录本轮针对「切图雪花 / 切图卡顿」两个现象的 RTL 修改。
**所有修改均为静态代码修复 + 参考模型验证，尚未经过综合、时序分析与上板波形确认。**

工程顶层：`src/user_source/hdl_source/top_tf_hdmi_audio.v`
实际链路：TF 卡 BMP → SDRAM 双缓冲 → HDMI，非图片 ROM 直读。

---

## 1. 修改清单

### 1.1 缓冲索引取反错误（最高置信，对应"切图雪花"）

`disp_buf_idx` / `write_buf_idx` 是 **2 位**寄存器，原代码用 `~disp_buf_idx` 求"另一块缓冲"：

| 表达式 | 输入 0 | 输入 1 | 结果 |
|---|---|---|---|
| 旧 `~disp_buf_idx` | `2'b00` | `2'b01` | **`2'b11` / `2'b10`** |
| 新 `disp_buf_idx ^ 2'b01` | `2'b00` | `2'b01` | `2'b01` / `2'b00` |

而顶层 `read_addr_2` / `read_addr_3` / `write_addr_2` / `write_addr_3` 全部接 `24'd0`，
因此索引 3 会映射到 **BUF0 基址 0** —— 显示 BUF0 时"预取备用图"实际写回 BUF0，
边显示边改写，直接产生切换附近的随机噪点/花屏。

**改动位置：**

- `SD/sd_card_bmp.v` 硬切分支、淡化完成分支、超时兜底分支、预取分支
  （原 `disp_buf_idx <= ~disp_buf_idx;` → `disp_buf_idx <= disp_buf_idx ^ 2'b01;`）
- `SD/sd_card_bmp.v` 预取：`pending_buf_idx` / `write_buf_idx`
- `top_tf_hdmi_audio.v` 第二读通道 `read2_addr_index`
- 同步更新了相关注释，避免后人再写回 `~`
- `top_tf_hdmi_audio.v` 新增仿真期自检：写缓冲与显示缓冲相同即报错

### 1.2 AXIS 行结束信号 `O_video_last` 不产生（对应行对齐/画面异常）

`video_rgb_to_axis_640x480.v` 原逻辑在行首把计数置 0、之后才递增，
而比较语句用的是**旧值**，导致第 640 个像素时计数为 638，
`S_x_cnt == 11'd639` 在 640 像素的行内**永远不会命中**。

修复：行首计数置 1，并仅在 `S_de_1d`（非行首）时比较 639。

### 1.3 `fade_start` 跨时钟域丢脉冲（对应"切图卡顿、按键无响应"）

原实现：100 MHz 域输出**单拍**脉冲 → 25 MHz 域两级采样 + 边沿检测。
10 ns 脉冲在 40 ns 周期内可能被完全漏采；一旦漏采，
`fade_pending` 永久为 1，后续所有按键请求被 `!fade_pending` 挡住且无超时 → 按键彻底失效。

修复（保持端口不变）：

- `sd_card_bmp.v`：`fade_start_pulse` 改为**保持型** `fade_req`，直到 `fade_done` 才拉低；
  25 MHz 侧原有的上升沿检测天然适配，不再依赖脉冲宽度。
- 新增 `fade_wait_cnt` + `fade_timeout`（2 秒）：osd 未响应时按**硬切**完成并消费请求，
  保证系统一定能回到可响应状态。
- `fade_done` 同步链由 2 级改为 **3 级**，边沿检测改用第 2/3 级（已完全同步），
  避免第一级亚稳态被当成有效脉冲。

### 1.4 扫描阶段按键长时间被屏蔽（对应"按下去不切/要按好几次"）

`bmp_read.v` 原逻辑：只有"找满 `scan_target_count` 张"或"扫到 `SCAN_MAX_SECTOR`"
才置 `scan_done`。顶层手动切换、自动轮播、首图加载全部以 `scan_done` 为条件。
卡内图片少于 8 张时（工程配置为 8 张，文档仍写"最多四张"），
需扫完 131071 个扇区（约 67 MB，SPI 逐扇区读）才响应，期间按键全部无效。

修复：新增 `SCAN_STALL_SECTORS`（16384 扇区 = 8 MB）。
已找到图之后，连续 8 MB 无新图即结束扫描。正常布局的卡行为不变，
图片数量不足时能快速进入可响应状态。

### 1.5 读通道标签队列无背压保护

`frame_read_write.v` 的"请求-响应配对准队列"深度 64，原代码没有满保护。
一旦在途请求超过深度，标签与返回数据会永久错位，之后所有像素路由错误 → 图像撕裂/花屏。

修复：新增 `tag_used` / `tag_room`，队列占用接近上限时暂停发出读请求
（在 `rd1_served` / `rd2_served` 处统一门控，保证 `burst_cnt` 计数与数据返回仍 1:1）。
同时把 `TAG_DEPTH`、`tag_bits`、`tag_wptr`、`tag_rptr` 的声明前移，消除前向引用。

### 1.6 转场/OSD 颜色运算通道串扰

`osd_engine.v` 的 `blend_w` 与 `alpha_blend` 把 24 位 RGB 当成**一个整数**做乘加/减法，
低位通道的进位会串到高位通道。例如 `bg = 0x000100` 时 `3*bg/4` 会算成 `0x0000C0`（绿色被清掉）。

修复：两个函数全部改为 **R/G/B 逐通道**运算。`blend_w` 单通道位宽取 13 位（255×16×2 = 8160）。
`alpha_blend` 逐通道 8 位运算不会溢出（已验证最大 255）。

## 3. 仍需上板确认的问题（本轮未改动）

以下几项属于设计权衡或需要实测数据，未擅自改动：

1. **读 FIFO 欠载**：`read_buf` / `read2_buf` 的 `empty_flag` 仍悬空。
   由于 FIFO 内部已有 `rd_en_s = !empty & re` 保护，不会读坏数据，
   但欠载会表现为重复像素。是否欠载取决于 SDRAM 带宽与双读仲裁，需要抓波形确认。
2. **`axis_s_ready` 未使用**：HDMI 核的 ready 已接出但发送侧未做反压。
   是否需要取决于该 IP 是否会拉低 ready，需查 IP 手册。
3. **扫描上限 `SCAN_MAX_SECTOR = 131071`**：本轮的收敛策略是"找到图后停"，
   若卡内图片分散在很远的位置，仍可能漏检，需要按实际卡布局确认。
4. **`req_cnt` 同拍多赋值**：按键事件与自动 tick 同拍时只加 1（不丢键，但可能少计一次），
   属于轻微行为差异，未改动。
5. **SDRAM 突发结束判定**：`frame_fifo_read` 用"停止发请求后延迟 10 拍"判定突发完成，
   自刷新导致的延迟变化是否影响它需要实测。

## 4. 第二轮：淡入淡出（交叉淡化）质量修复

现象：切图已不卡顿，但淡化转场"效果不好"。

### 4.1 根因：转场结尾会"跳回旧图"一整帧

`osd_engine.v` 原 `FADE_ST_RUN` 在 `fade_w` 降到 0 时**立刻**回到 `FADE_ST_IDLE`：

```
if (fade_w == 5'd0) begin
    fade_state  <= FADE_ST_IDLE;   // ← 立刻回 IDLE
    fade_done_r <= 1'b1;
end
```

回到 IDLE 后 `bg_eff` 立刻切回 `bg_pixel`（ch1），但此刻 **ch1 仍然指向旧缓冲**：

- `disp_buf_idx` 要等 `sd_card_bmp` 跨 100 MHz/25 MHz 同步后才翻转；
- 即使翻转了，ch1 的 `read_addr_index` 也要到**下一个 vs 沿**才被 `frame_fifo_read` 锁存。

于是画面序列变成：`… 混合(1/16) → 新图(100% ch2) → 旧图(ch1) → 新图(ch1) …`
中间那一帧旧图就是肉眼看到的闪跳。

用参考模型复现（`doc/convert/fade_ref_check.py`）：

```
修复前 出现'新图→旧图'回跳的帧号: [35, 72]
修复后 出现'新图→旧图'回跳的帧号: 无
```

### 4.2 修复：新增 `FADE_ST_HOLD` 保持态

```
IDLE → ARM(等 2 帧对齐) → RUN(64 档淡化) → HOLD(保持新图 3 帧) → IDLE
```

- **RUN** 结束时（`fade_w == 0`）不再回 IDLE，而是进入 **HOLD** 并发 `fade_done`；
- **HOLD** 期间 `bg_eff = bg_pixel_alt`（ch2 = 新图），`fade_rd` 保持有效，画面连续；
- 等 `sd_card_bmp` 完成缓冲翻转、且 ch1 在下一个 vs 沿锁存到新基址之后，HOLD 才回 IDLE；
- 回到 IDLE 时 ch1 已经在新缓冲上，`bg_eff` 切回 ch1 **无跳变**。

### 4.3 同步改进：档数 16 → 64，时长 0.53 s → 1.07 s

原实现 16 档、每档 2 帧，阶梯感明显。改为：

| 参数 | 位置 | 默认值 | 含义 |
|---|---|---|---|
| `FADE_MAX` | `osd_engine.v` | `64` | 淡化档数，越大越平滑（须为 2 的幂） |
| `FADE_SHIFT` | `osd_engine.v` | `6` | 归一化右移位数，必须等于 `log2(FADE_MAX)` |
| `FADE_STEP_DIV` | `osd_engine.v` | `1` | 每档保持帧数，越大越慢 |
| `HOLD_FRAMES` | `osd_engine.v` | `3` | HOLD 保持帧数，需覆盖缓冲翻转 + ch1 重新锁址 |

时长 = `FADE_MAX × FADE_STEP_DIV + HOLD_FRAMES` 帧 ≈ `64×1+3 = 67` 帧 ≈ **1.12 s**。

`blend_w` 相应改为按 `FADE_SHIFT` 归一化，单通道位宽扩到 16 位（255×64 = 16320）。
`sd_card_bmp.v` 的 `FADE_TIMEOUT_CYCLES` 由 2 s 提到 **3 s**，
保证超时阈值大于完整转场时长（否则长淡化会被误判为"osd 无响应"而提前硬切）。

### 4.4 SW1 中途拨回硬切档的处理

原实现中途拨回会从"半混合"直接翻转缓冲，产生一次跳变。
现改为：立即把 `fade_w` 置 0 并进入 HOLD —— 画面直接呈现新图，随后翻转无缝衔接。

### 4.6 可能仍影响观感、但本轮未改的点

1. **OSD 红条与滚动字幕不参与淡化**：`osd_engine` 的 L0/L1 图层是在 `bg_eff` 之上以 100% 不透明叠加的，
   所以画面底部红条在转场期间保持实心。若希望它一起淡化，需要把 `bg_eff` 与图层混合的权重联动。
2. **ch1 / ch2 共用 `read_en`，但各自独立判空**：若某一通道 FIFO 瞬时读空，
   两路会错开一个像素并保持错开，混合图上会出现轻微横向错位/重影。
   彻底解决需要把两个 FIFO 的 `empty_flag` 引出、用"两路都非空"作为共同读使能。
   当前 FIFO 深度 512、两路合计带宽占用约 30%，正常情况下不应触发，需抓波形确认。
3. **淡化期间 ch2 的读突发未参与写侧仲裁**：`frame_read_write` 中 ch2 的 `O_rd_busy` 悬空，
   写 FSM 只用 ch1 的 `App_rd_busy` 做互斥。若淡化期间同时有预取写入，SDRAM 会有额外竞争，
   建议抓 `App_wr_en` 与 `Sdr_rd_en` 确认。

## 6. 第三轮：时序收敛 + "图片不会逐渐浮现"根因诊断

### 6.1 先修掉上一轮我自己引入的一个 bug（`tag_used` 回绕）

`frame_read_write.v` 里给标签队列加的背压，占用算法写错了：

```verilog
// 错：先零扩展到 7 位再相减
wire [6:0] tag_used = {1'b0, tag_wptr} - {1'b0, tag_rptr};
wire       tag_room = (tag_used < (TAG_DEPTH - 8));
```

`tag_wptr` / `tag_rptr` 是 **64 深循环队列**指针（6 位）。零扩展到 7 位后再相减，
当 `rptr` 越过回绕点（例如 `wptr=8, rptr=60`）时，真实占用只有 12，
却会算成 `8-60 = -52 → 7 位无符号 76`，远超阈值 56。

修复：

```verilog
wire [5:0] tag_used = tag_wptr - tag_rptr;   // 6 位减法 = mod 64，占用 0..63
wire       tag_room = (tag_used < 6'd56);    // 留 8 项余量
```

### 6.2 用周期级模型证明：读数据通路本身是**正确**的

新增 `doc/convert/rdpath_ref_check.py`，把「双读仲裁 + 请求-响应配对标签队列 +
两个读 FIFO」按 `mem_clk` 逐拍建模，SDRAM 建模为固定延迟返回。

| 场景 | 路由错配 | ch1 稳态最低水位 | ch2 稳态最低水位 | 被背压挡住的拍数 |
|---|---|---|---|---|
| 单读（ch1 only） | **0** | 381 | — | 0 |
| 双读 + 修复后 `tag_used` | **0** | 381 | 381 | 0 |
| 双读 + 修复前 `tag_used`（7 位） | **0** | 381 | 381 | 11377 / 40000（28%） |

结论（重要，且是**否定性**的）：

1. **路由错配恒为 0** —— 标签队列把 ch2 请求的数据正确地送进了 ch2 的 FIFO，
   仲裁轮换、地址计数、FIFO 填充都没有问题。**读通路不是"淡化不出现"的原因。**
2. 6.1 那个 `tag_used` bug 只是把读吞吐压低约 28%，在双读约 30% 带宽占用下
   仍不足以抽干 FIFO（最低水位仍有 381/512）。**它是性能缺陷，不是功能缺陷**，
   修它是为了恢复余量，不要指望它治好淡化。
3. 两路 FIFO 在帧首被同一个 `vs` 沿清空、被同一个 `read_en` 抽取、
   基址又分别是 `disp_buf_idx` 与 `disp_buf_idx^1`，**天然对齐**，
   不存在"新旧图错位一个像素"的问题。

### 6.3 真正的头号嫌疑：`sw_fade` 读到 0，转场状态机根本没被启动

排查链路：

- `sd_card_bmp` 只有在 `sw_fade_sync == 1` 时才走"发 `fade_req`"分支，
  否则直接 `disp_buf_idx <= disp_buf_idx ^ 1` **硬切**；
- `osd_engine` 的 `fade_start_sync` 只由 `fade_start`（= `fade_req`）驱动。

也就是说 **`sw1` 读成 0 时，整条淡化链路一次都不会被执行**，
现象就是"图片直接跳过去、完全没有逐渐浮现"——与用户描述完全一致。

而 `sw1` 的可疑之处：

- 参考例程（`设计参考例程文档.md`）的 I/O 表里**只有 key1 / key2，没有拨码开关**；
- `pin.adc` 里 `sw1` 绑在 **C8**，且原约束是 `PULLTYPE = NONE`（无内部上下拉）。
  引脚若悬空/未接，CMOS 输入电平不确定，实测很容易被读成 0。

**修复**：`pin.adc` 的 `sw1` 改为 `PULLTYPE = PULLUP`，使"开关断开/未接"读成 1（= 淡化）。

**并加了一条可视化诊断**：把 `osd_engine` 的 `fade_state` 引到数码管第 4 位
（0=IDLE 1=ARM 2=RUN 3=HOLD）。这样上板时：

- 按 key1 时这一位恒为 **0** → 转场状态机没启动 → 看第 5 位是 `F` 还是 `C`；
  若是 `C`，说明 SW1 被当成硬切档（检查 C8 那个开关/跳线）；
- 能看到 **0→1→2→3→0** 跳变 → 转场流程在跑，问题就落到混合数据上，
  再去抓 `bg_pixel_alt` / `rd2usedw`。

### 6.4 时序根本没有收敛（实测数据）

从 `HDMI1.4b_Transmitter_v1.0_Runs/phy_1/route.qor` 与 `final_timing.rpt`：

```
Setup WNS = -6699ps   Setup TNS = -300388ps   违例端点 75 个
Hold  WNS =     3ps   Hold  TNS =      0ps    违例端点  0 个
```

按时钟域拆分：

| 时钟 | 约束频率 | 实测可达 | SWNS | STNS |
|---|---|---|---|---|
| `video_clk` | 25 MHz | 38.4 MHz | +3.545ns | 0 |
| `sd_card_clk` | 100 MHz | 64.0 MHz | **-1.125ns** | -1.895ns |
| `ext_mem_clk` | 125 MHz | **46.7 MHz** | **-6.699ns** | **-216.819ns** |
| `hdmi_5x_clk` | 125 MHz | 266 MHz | +4.241ns | 0 |

去掉引脚类伪违例后，**真正的片内违例**是：

```
Path Group : ext_mem_clk -> ext_mem_clk    Min Period 8.447ns   Fmax 118.385MHz
Begin Point: frame_read_write_m0/write_buf/rd_addr_reg[0]
End   Point: frame_read_write_m0/frame_fifo_read2_m0/state_reg[1]   Slack -0.410ns
End   Point: frame_read_write_m0/frame_fifo_read_m0/state_reg[3]    Slack -0.410ns
```

即一条**跨三个状态机**的长组合链：

```
写 FIFO 内部 gray 指针 → rdusedw → frame_fifo_write.into_burst
   → O_wr_busy → App_wr_busy → 两个读 FSM 的 S_CHECK_FIFO 判据
```

读 FSM 一旦采到错误的 `App_wr_busy`，就会跳过或延迟一次突发，造成读 FIFO 欠载。
（`into_burst` 里还含一个 21 位加法 + 比较：`write_len_latch <= (rdusedw + write_cnt)`。）

**修复（不改互斥语义，只插一级流水）**：

- `frame_fifo_write.v`：`rdusedw` 先打一拍成 `rdusedw_r` 再参与 `into_burst`；
- `frame_fifo_read.v`：`wrusedw` 先打一拍成 `wrusedw_r` 再参与 `S_CHECK_FIFO`。

这两个都只是"攒够一次突发的数据没有"的流量阈值，晚一拍判断对功能无影响，
但把长链切断，让 125 MHz 域有机会收敛。

### 6.5 SDC：把伪违例清掉，让真违例露出来

原 `timing.sdc` **完全没有写 Input/Output delay**（文件里自己写着"先保持空白"）。
后果：

### 7.1 问题一：按键静置很久后第一次切图出现雪花

用户给了三条推测，逐条核对：

| 用户要求 | 现状 | 处理 |
|---|---|---|
| 按键输入增加两级同步打拍 | **已满足**：`key_press_debounce` 内已有 `button_sync0/1` 两级；`sw1` 在 `sd_card_bmp` / `osd_engine` 各有两级 | 无需改，已确认 |
| 切图必须等 vsync 消隐窗口再软复位读 FIFO | **已满足**：`read_req` 由 vs 下降沿产生，读 FSM 在 `S_ACK` 拉高 `fifo_aclr`，天然落在场消隐期；`disp_buf_idx` 也要等 `S_ACK` 才被锁存 | 无需改，已确认 |
| tag 逻辑去除固定打拍、适配动态读延迟 | **部分满足**：数据路由早就不是固定延迟，但突发结束仍写死 10 拍 | **已改**，见下 |

**本轮真正找到的两个缺陷：**

**(a) 按键/复位引脚没有内部上拉（`PULLTYPE = NONE`）**

`key_press_debounce` 的注释明确写着"默认：松开=1，按下=0"——即按键是**按下接地**型。
但 `pin.adc` 里 `key1/key2/rst_n` 全是 `PULLTYPE = NONE`。
按键松开时引脚**悬空**，CMOS 输入电平随漏电/温漂缓慢漂移；
"很久没按"正好对应"长时间悬空"，第一次按下时边沿不干净，
消抖状态机可能产生错误/多余脉冲 → 切图行为异常。

修复：`key1` / `key2` / `rst_n` 全部改 `PULLTYPE = PULLUP`（`sw1` 上一轮已改）。

**(b) 写 FIFO 被抽空后仍继续读（`empty_flag` 悬空）**

`frame_fifo_write` 的突发一旦启动，`App_wr_en_d0` 只检查
`burst_cnt < BURST_SIZE` 和 `write_cnt < write_len_latch`，**不检查写 FIFO 里还有没有数据**。
若 TF 卡长时间静置后首次访问响应变慢、或读卡中途停顿，
写 FIFO 会被抽干，而 FIFO 空时 `dout` 保持上一次的值 →
**把陈旧数据当图像写进 SDRAM → 那一张图出现雪花**；
而 `write_finish` 照常拉高，坏图照样被提交显示。这正好解释"静置后第一次、再按就好"。

修复：突发中途加 `&& (rdusedw_r != 0)` 门控。数据没到就等，SD 恢复后自动继续；
若一直不到，`bmp_read` / `sd_card_bmp` 的 2 秒超时会放弃本次加载，**不会显示坏图**。

**(c) tag 突发结束判据动态化（用户明确要求）**

`frame_fifo_read.v` 原来：

```verilog
assign rd_burst_finish = (rd_vld && rd_delay == 4'd10);   // 写死 10 拍
```

改成按"在途请求数归零"判定：

```verilog
// 请求被服务 +1，本通道数据返回 -1
case ({App_rd_ack, Sdr_rd_en})
    2'b10:   rd_inflight <= rd_inflight + 1'b1;
    2'b01:   rd_inflight <= (rd_inflight != 0) ? (rd_inflight - 1'b1) : rd_inflight;
    default: rd_inflight <= rd_inflight;
endcase
assign rd_burst_finish = (rd_vld && (rd_inflight == 0)) || (rd_vld && rd_delay == 4'd15);
```

`rd_delay == 15` 只作**防死锁安全网**（请求被丢弃时不至于卡死），不再是主判据。
自刷新/预充电/激活导致的返回延迟变化不再影响正确性。

**(d) 两路读 FIFO 对齐门控**

转场时两个读 FIFO 用同一个 `read_en` 抽取。若一路先空（FIFO 内部会停住），
另一路照常推进 → 两路永久错开一个像素 → 混合时横向重影。
修复：引出两路 `empty_flag`，转场期间只要有一路空就一起暂停：

```verilog
wire read_en_g = read_en & ~(read2_en & (rd1_empty | rd2_empty));
```

顶层把 `read2_en` 由 `video_read_en` 改成 `video_read_en & fade_rd`，
非转场期间这条门控自动失效，不影响平时单路显示。

### 7.2 问题二：转场重做（亮度淡入 FADE + 纵向逐行擦除 WIPE）

原实现是"新旧图交叉淡化"，与用户想要的"**整图从全黑平滑浮现**"不是同一种效果，
而且用户看到的是"抖动一下、变模糊"。本轮按要求重做，**OSD 图层逻辑一行没动**。

**状态机（保留原有 4 态结构，只换进度量）：**

```
IDLE → ARM(等 2 帧对齐) → RUN → HOLD(保持新图 3 帧等缓冲翻转) → IDLE
```

**两种效果（由 SW1 选择，接口不变）：**

| SW1 | 效果 | 公式 / 规则 | 时长 |
|---|---|---|---|
| 1 | **整图亮度淡入** | `out = (img * alpha) >> 8`，alpha 0→255 | 65 帧 ≈ 1.08s |
| 0 | **纵向逐行擦除** | `y >= wipe_line` 用新图，否则用旧图；wipe_line 480→0 | 61 帧 ≈ 1.02s |

**关键约束（用户明确要求，已逐条落实）：**

1. **进度量只在 vsync 场消隐期更新**：`alpha` / `wipe_line` 的更新全部包在
   `if (vs_fall)` 里，DE=1 期间**逐位不变** → 同一帧内所有有效像素用同一个值，
   不存在帧内撕裂/横向阴影。参考模型专门对比了"帧中途更新"（帧内会出现 2 种取值）。
2. **8bit 定点 alpha**：`ALPHA_MAX = 8'd255`，逐通道 `(pix * a) >> 8`，
   单通道最大 `255*255 = 65025 < 65536`，16 位不溢出。
3. **像素流水线对齐**：`wipe_line` 比较用的 `pixel_y` 与 `bg_pixel` / `bg_pixel_alt`
   在顶层由**同一个延迟后的 `de`** 对齐产生，前景/背景天然逐像素对齐。
4. **WIPE 方向**：`y >= wipe_line` 用新图、`wipe_line` 每帧减小
   → 屏幕**下方先变**、向上推进（与用户描述的效果一致）。
5. **不破坏 SDRAM 帧读通路**：只改 `bg_eff` 的选择逻辑与输出级一次乘法，
   读通路、FIFO、仲裁、缓冲翻转时序全部未动。

**两处需要用户确认的取舍：**

- **硬切模式已去掉**：`sd_card_bmp` 原来在 `SW1=0` 时直接硬切，
  这会让用户看到"完全没有转场效果"。现在切图**一定**走转场，SW1 只选效果。
- **`FADE_INCLUDE_OSD`（`osd_engine.v` 顶部 localparam，默认 `1'b1`）**：
  FADE 模式下是否让整幅画面（含 OSD 字幕/红条）一起从黑浮现。
  置 `1'b0` 则只淡化底图、字幕保持常亮（即完全不动 OSD 输出）。
  WIPE 模式下 OSD 输出与原来逐位一致。

### 8.1 参考工程 `1/lab_ex5_i2s` 是什么

## 9. 第六轮：模式 1 改为"交叉淡化"（旧图渐暗 + 新图渐显）

### 9.1 改了什么

| | 改前（上一轮） | 改后（本轮） |
|---|---|---|
| 模式 1 公式 | `out = (新图 * alpha) >> 8` | `out = (旧图 * (255-alpha) + 新图 * alpha) >> 8` |

3. 删掉输出级那一次整体乘 alpha（它只服务于旧的"从黑浮现"），

## 11. 第八轮：把两条切图路径彻底拆开（修复"模式 2 不切图"）

用户反馈：**模式 2 下按键，图片完全不切换**。

### 11.1 根因：两条路径被耦合在一起

重构前的"换图动作块"是这样的（`sd_card_bmp.v`）：

```verilog
if (req_cnt != 3'd0 && pfb_valid && display_valid && !fade_pending) begin   // ← 耦合点
    if (sw_fade_sync) begin
        fade_req <= 1'b1; fade_pending <= 1'b1;        // 路径 A:转场
    end else begin
        disp_buf_idx <= disp_buf_idx ^ 2'b01;          // 路径 B:硬切
    end
end
```

**整块（含硬切）都被套在 `&& !fade_pending` 里**。只要模式 1 的转场状态
`fade_pending` 残留为 1（例如转场途中拨动 SW1、或某次 `fade_done` 没被采到），
**模式 2 的硬切也会被一起挡住**，表现就是"按了不切图"。
（而且上一轮把 `FADE_TIMEOUT_CYCLES` 从 3s 提到 5s，这个卡顿窗口也被拉长了。）

### 11.2 修复：两套完全独立的路径

```verilog
if (sw_fade_sync) begin
    // ============ 路径 A:淡入淡出转场 ============
    if (req_cnt != 3'd0 && pfb_valid && display_valid && !fade_pending) begin
        fade_req <= 1'b1; fade_pending <= 1'b1;        // 发起转场
    end
    if (fade_done_pulse && fade_pending) begin ...翻转... end   // 等 osd 完成
    else if (fade_timeout)               begin ...翻转... end   // 超时兜底
end else begin
    // ============ 路径 B:直接切换(硬切) ============
    fade_req <= 1'b0; fade_pending <= 1'b0;            // 顺手清干净
    if (req_cnt != 3'd0 && pfb_valid && display_valid) begin   // ← 不再看 fade_*
        disp_buf_idx <= disp_buf_idx ^ 2'b01;
        ...
    end
end
```

| | 路径 A | 路径 B |
|---|---|---|
| 触发条件 | 有请求 **且** 没有正在进行的转场 | **只**看"有请求 + 备用缓冲就绪" |
| 用到的状态 | `fade_req` / `fade_pending` / `fade_done` / `fade_timeout` | **完全不看 `fade_*`** |
| 涉及模块 | `osd_engine` + `sd_card_bmp` | 只有 `sd_card_bmp` |

**两条路径唯一的共同点只是"翻转 `disp_buf_idx` / 提交 `pfb`"这几个赋值**，
触发条件与状态变量各自独立 —— 所以现在可以一条一条单独调试。

### 11.3 顺带清掉的东西

模式 2 里之前还残留着一套"可选纵向逐行擦除"（`MODE2_HARDCUT` / `MODE2_EFFECT` /
`wipe_line` / `WIPE_TOP` / `WIPE_STEP` / `wipe_out`）。它让模式 2 的代码不再是
"纯硬切"，也让路径选择多了一层条件。本轮**全部删除**，模式 2 现在就是干净的硬切。

| 删除项 | 原位置 |
|---|---|
| `localparam MODE2_HARDCUT` | `sd_card_bmp.v:44–48` |
| `localparam MODE2_EFFECT` | `osd_engine.v:126` |
| `wipe_line` / `WIPE_TOP` / `WIPE_STEP` / `wipe_out` / RUN 里的擦除分支 | `osd_engine.v` 多处 |

> 如果以后还想要"逐行擦除"这个效果，可以再加回来；但要注意它和模式 1 会争同一个
> 开关（SW1 只有两个档位），需要另想办法选择（例如用按键长按）。

## 12. 第九轮：模式 1 的"一次按键 = 一个完整循环"（模式 2 未改动）

用户要求：按下切图键后，画面**最亮 → 最暗（此时切图）→ 最亮**，
**这一个循环完成后就保持最亮不动**，不要再闪，等待下一次按键。

### 12.1 本轮改动（只动 `osd_engine.v`，模式 2 的代码一行未动）

IDLE 状态原来用**单拍上升沿**检测转场请求：

```verilog
assign fade_start_sync = fs_d0 & ~fs_d1;   // 旧写法
if (fade_start_sync)  begin ... end
```

问题：如果请求的上升沿正好出现在 osd 还忙着的时候（例如上一次转场刚结束、
osd 还在 HOLD 的 3 帧里），这个单拍脉冲会被**漏掉**；
而 `fade_req` 是保持型信号，漏掉后它会一直悬着，
只能等 `FADE_TIMEOUT_CYCLES`（5 秒）超时兜底 → 表现为"卡一下然后硬切/闪一下"。

改成用**同步后的电平**判断：

```verilog
reg  fs_d0, fs_d1;
always @(posedge clk or posedge rst) begin
    if (rst) begin fs_d0 <= 1'b0; fs_d1 <= 1'b0; end
    else begin fs_d0 <= fade_start; fs_d1 <= fs_d0; end
end
// IDLE:
if (fs_d1) begin                      // 电平:有没有转场请求
    fade_state <= FADE_ST_ARM;
    arm_cnt    <= 2'd0;
end
```

因为 `fade_req` 本身就是"整段转场期间为 1、转场结束才拉低"的保持型信号，
用电平判据既不会漏请求，也不会自激：转场跑完回到 IDLE 时它已经是 0，
于是**停在最亮不动**，直到下一次按键再把它拉高。

### 12.2 循环结构（一次按键 = 一个循环）

```
按键 → req_cnt=1 → 路径A发 fade_req(保持为1)
     → osd: IDLE → ARM(2帧) → RUN 前半段 旧图 255→0 (65帧)
                             → 黑场(alpha=0,2帧,切图发生在这里)
                             → RUN 后半段 新图 0→255 (65帧)
                             → HOLD(3帧,等 disp_buf_idx 翻转生效)
                             → IDLE(回到最亮,停住)
     → fade_done → sd_card_bmp 翻转缓冲、清 fade_req
     → 停在最亮,等待下一次按键
```

### 12.3 本轮验证

| 验证项 | 结果 |
|---|---|
| 一次按键跑完回到 **IDLE**（停在最亮，不再自动开始第二个循环） | 通过 |
| 亮度曲线单调、切图点在全黑帧、无结尾回跳、时长 2.22s < 5s | 通过（回归） |
| 两条路径互不干扰 | 通过（回归） |
| 结构配平（3 个文件） | 通过 |
| `logic_ref_check` / `rdpath_ref_check` | 通过 |
| 综合 / 时序 / 上板 | **未执行** |

### 12.4 ⚠️ 关于"一直闪烁"——很可能是按错键了

代码里两个按键的定义（`top_tf_hdmi_audio.v:5-6`）：

```verilog

input  key2,   // 自动播放 开/关
```

**KEY2 是"自动轮播开关"，不是"切下一张"。** 按一下 KEY2 就会开启轮播，
之后**每 1 秒自动产生一次切图请求** → 淡入淡出循环就会一直跑，
看起来就是"画面不停地变暗变亮、停不下来"。

手动切一张请按 **KEY1**；想停掉轮播再按一次 **KEY2**。

> 这个按键语义是赛题基础要求第 (3) 条明确规定的
> （"其中一个按键用于手动切换至下一张，另一个用于启动/停止自动轮播"），
> 所以默认不能改。如果你确实希望 KEY2 也是"按一次切一张"，告诉我一声，
> 但那样会丢掉"自动轮播"这项基础分。


## 13. 第十轮：消除模式 1 淡化"结束后还会闪一下"（字幕保持常亮）

用户反馈两点：
1. 模式 1 的两段式淡化跑完、画面已经回到最亮之后，**结尾还会闪一下**；
2. **字幕红条要保持常亮**，不要跟着一起变暗。

### 13.1 根因：结尾的"新图 → 旧图 → 新图"回跳

第九轮的写法是"**前半段显示 ch1(旧图)、后半段显示 ch2(新图)**"，
而 `fade_done` 在**后半段结束**时才发出，`sd_card_bmp` 收到后才翻转 `disp_buf_idx`：

```
后半段   : bg_eff = bg_pixel_alt = ch2 = (disp_buf_idx ^ 1) = 新图   ✅
后半段结束: fade_done → disp_buf_idx ^= 1
HOLD     : bg_eff = ch2 = (disp_buf_idx ^ 1) → 变成"旧图"          ❌ 闪一帧旧图
回 IDLE  : bg_eff = ch1 = 新图                                       ✅
```

也就是 `read2_addr_index = disp_buf_idx ^ 2'b01` 这个表达式，
在 `disp_buf_idx` 翻转之后自动指向了**旧缓冲**，于是结尾出现
"新图 → 旧图 → 新图"的闪帧。这正是用户看到的"结束后闪一下"。

### 13.2 修复（只动 `osd_engine.v`，模式 2 一行未动）

**① 把 `fade_done` 从"后半段结束"挪到"全黑那一帧"。**

```verilog
if (!fade_half) begin
    if (alpha == 8'd0) begin
        fade_half   <= 1'b1;     // 切到后半段
        fade_done_r <= 1'b1;     // ★ 在"全黑"这一帧就通知翻转显示缓冲
    end                          //   切图动作藏在全黑里,肉眼看不到
    else if (alpha <= ALPHA_STEP) alpha <= 8'd0;
    else alpha <= alpha - ALPHA_STEP;
end else begin
    // 后半段不再发 fade_done —— 缓冲已经在全黑时翻过了
    if (alpha >= ALPHA_MAX) begin fade_state <= FADE_ST_HOLD; hold_cnt <= 2'd0; end
    else if (alpha + ALPHA_STEP >= ALPHA_MAX) alpha <= ALPHA_MAX;
    else alpha <= alpha + ALPHA_STEP;
end
```

**② 全程只显示 ch1，不再切换像素来源。**

```verilog
wire [23:0] bg_eff = bg_pixel;   // 全程 ch1
// 旧写法: wire [23:0] bg_eff = fade_half ? bg_pixel_alt : bg_pixel;
```

前半段 ch1=旧图 → 全黑帧翻转 → 后半段 ch1 自动变成新图。
**全程只有一个来源，不存在"源切换"，所以结尾不可能回跳。**

**③ 关闭第二读通道**（两段式同一时刻只需要一张图）：

```verilog
assign fade_rd = 1'b0;
```

好处：转场期间 SDRAM 读出带宽减半（约 15% 而不是 30%），
也不再需要两路读 FIFO 对齐。端口 `bg_pixel_alt` 保留以维持模块接口。

**④ 字幕/红条保持常亮**（用户明确要求）：

```verilog
localparam FADE_INCLUDE_OSD = 1'b0;   // 只缩放底图,OSD 输出完全不碰
```

亮度缩放只作用在底图 `bg_eff` 上；OSD 两层混合结果直通，红条/字幕恒定最亮。

### 13.3 为什么"翻转挪到全黑帧"是安全的

读地址通路本来就支持"帧边界换缓冲"（`SD/frame_fifo_read.v`）：

- `read_addr_index` 在 `mem_clk` 域做了**两级同步**（`read_addr_index_d0/d1`）；
- 基址只在 `S_ACK`（新一次读请求）时**锁存**（`App_rd_addr_r <= read_addr_x`），
  同时 `fifo_aclr <= 1'b1` **清读 FIFO**。

所以 `disp_buf_idx` 翻转后，**下一帧从新缓冲的帧首重新开始读**，
不会出现帧内地址跳变，也不会读到上一缓冲的残留像素。

## 15. 第十五轮：模式 1"反复变暗变亮、图片不换"根因修复（2026-10-05）

### 15.1 现象

SW1=1（两段式淡入淡出）下按一次手动切图键后：**图片只切一次，随后屏幕持续反复
"变暗→变亮"、不再切换图片**；数码管稳定读数为 `221`
（`fade_state = RUN` / `state_code = 读卡` / SW1=1）。

### 15.2 根因：8 位加法回绕 → FSM 卡死在 RUN

`osd_engine.v` 后半段（FADE_IN，alpha 0→255 增亮）的**增量饱和判断**用了 8 位加法：

```verilog
end else if (alpha + ALPHA_STEP >= ALPHA_MAX)   // ← 8 位加法
    alpha <= ALPHA_MAX;
else
    alpha <= alpha + ALPHA_STEP;
```

`ALPHA_STEP = 8` 时 `alpha = 248 → 248 + 8 = 256`，8 位加法**回绕成 0**，
于是 `0 >= 255` 恒为假 → 走 else 把 alpha 赋成回绕后的 **0**。
结果 alpha 永远在 `0 → 8 → … → 248 → 0` 之间循环，**升不到 255**，
`alpha >= ALPHA_MAX` 分支永远进不去 → `fade_state` 永远停在 `FADE_ST_RUN`。

- **画面表现**：每约 32 帧一段"黑 → 渐亮 →（回绕）黑"，即"反复变暗变亮"；
- **为什么图片不再切换**：FSM 卡在 RUN，永不回 IDLE，`fade_req` 电平不释放，
  `req_cnt` 里的后续请求永不被消费、预取不再启动 → 图不变；
- **为什么以前没发现**：该 bug 自"两段式转场"引入起就存在。FADE_OUT（递减）有
  `alpha <= ALPHA_STEP` 的**下溢保护**，所以变暗那半段一直正常；只有 FADE_IN 的
  **增量饱和**踩了回绕。且 Python 参考模型用无限宽整数，不回绕，测不出来。

### 15.3 修复（1 行，最小改动）

把饱和比较从 8 位扩到 9 位：

```verilog
end else if ({1'b0, alpha} + {1'b0, ALPHA_STEP} >= {1'b0, ALPHA_MAX})   // ← 9 位，256>=255 成立
    alpha <= ALPHA_MAX;
else
    alpha <= alpha + ALPHA_STEP;   // 到这里 alpha+STEP ≤ 254，8 位赋值不回绕
```

- 三个操作数都零扩展到 9 位；`255 + 8 = 263 < 512`，9 位足够；
- 未改动 FSM 任何状态、任何其它逻辑、任何参数——**单行定点修复**；
- 对应 `osd_engine.v` 第 ~260 行，原地替换，行数与上下文结构不变。

### 15.4 参考模型补强（让它能复现 bug）

`doc/convert/fade_ref_check.py`：
1. 新增 `w8(x) = x & 0xFF` 模拟 RTL **8 位寄存器回绕语义**——这是此前漏检的根本原因（模型与 RTL 位宽语义不一致）；
2. `osd_step(..., buggy=False)` 增加双路径：`buggy=True` 用 8 位回绕比较复现旧 RTL，`buggy=False` 用 9 位比较对应修复后 RTL；
3. 新增 `check_overflow_bug()`，对照展示修复前卡死在 RUN、修复后收敛到 HOLD；并计入 `main()` 总判定。

| | 修复前 (buggy) | 修复后 |
|---|---|---|
| alpha 轨迹尾段 | …168, 176, 184 | …240, 248, **255** |
| 能否升到 255 | 否 | 是 |
| 结束状态 | **卡死 RUN** | 收敛 HOLD |

## 16. 第十六轮：自动轮播"停止不及时"（按 key2 后仍多切约 2 张）（2026-10-05）

### 16.1 现象

SW1=1（淡入淡出）下按 key2 启动自动轮播，再按 key2 停止：
**理论应立即停止，实际图片仍继续切换约 2 张（每张一次完整淡入淡出）才停住。**
硬切模式（SW1=0）无此现象。

### 16.2 完整控制链

```
key2 ──► 消抖 20ms ──► key_auto_press ──► auto_play_en 取反 + auto_cnt 清零(当拍生效)
                                            │
                                            ▼
                                     auto_cnt 1s 定时器 ──► auto_tick
                                            │
                                            ▼
                          req_cnt 请求队列(0~7 饱和)◄── key1 手动切图也汇入此处
                                            │  req_cnt≠0 && pfb_valid && !fade_pending
                                            ▼
                        fade_req(保持型) ──► osd_engine FSM(跨到 25MHz video_clk)
                        IDLE→ARM(2帧)→RUN 变暗(32帧)→【全黑帧发 fade_done】
                                     →RUN 变亮(32帧)→HOLD →IDLE   共 ≈73 帧 ≈1.22s
                                            │  fade_done 跨回 100MHz
                                            ▼
                        翻转 disp_buf_idx, img_idx←pfb_idx, req_cnt−1
                                            │
                                            ▼
                        (独立) 预取: !pfb_valid 就把后继图读进备用缓冲
```

### 16.3 根因：`auto_play_en` 管不到 `req_cnt` 存量

- `auto_play_en` 的作用范围**只有两处**：门控 `auto_cnt` 计数、门控 `auto_tick → req_cnt++`
  的**汇入**。它**不**控制：req_cnt 存量、fade_req 发起、提交点（img_idx 更新）、预取。
- `req_cnt` 是**饱和队列**（0~7），与 key1 手动切图共用；`auto_play_en=0` 后存量照样逐个执行。
- **排队速度 > 消化速度**：tick 每 1s 排 1 个，而一次完整转场要 73 帧 ≈1.22s 才消化 1 个
  → req_cnt 持续积压。参考模型：轮播 10s→存量 3，20s→5，30s→6，40s 后饱和到 7。
  （用户实测"约 2 张"对应轮播约 7~8s 后按停止。）
- **在途转场不可撤销**：`osd_engine` 的 ARM/RUN/HOLD **无取消入口**，RUN 态连 `fade_req`
  被拉低都不检查，一发必跑完；且切图（缓冲翻转）发生在**全黑帧**（转场第 35 帧），
  不是转场结束那一帧。
- `key_auto_press` 当拍只做了 `auto_play_en` 取反 + `auto_cnt` 清零（这两点本身没问题，
  响应是当拍即时的），**漏了清 req_cnt**。

### 16.4 采用方案 B（最小改动，只清存量）

对比过两个方案：

| | 改动 | 效果 | 取舍 |
|---|---|---|---|
| A | 关闭当拍清 `req_cnt` + 撤 `fade_req` + 清 `fade_pending` | 停止后 **0 张**（在途转场也在全黑帧后淡回当前图） | 会连带丢弃混入队列的手动 key1 请求；关闭瞬间画面有一次"变暗→黑→淡回" |
| **B（采用）** | 关闭当拍只清 `req_cnt` | 停止后 **≤1 张**：恰在转场前半段按停止 → 在途那一次正常切完；在后半段按 → 0 张 | 与 key1 手动请求共用队列，逻辑最简单、风险最低 |

`sd_card_bmp.v` 换图动作块之后新增 3 行（含注释共 10 行）：

```verilog
// ★ 停止自动轮播的当拍：丢弃尚未开始的排队请求（req_cnt 存量）。
if (key_auto_press && auto_play_en)
    req_cnt <= 3'd0;
```

三个要点：
1. 条件 `auto_play_en` 为 1 表示"本次按键是关闭"，开启时不清队列；
2. 语句放在**换图动作块之后**（同一 always 块内靠后的赋值优先），这样与
   `fade_done_pulse` 恰好落在同一拍时，清零优先于该分支的 `req_cnt` 自减，
   不会漏掉一个残留请求；
3. 未改动 `osd_engine`、未改动 FSM、未改动任何参数与其他逻辑。

### 16.5 参考模型（新增 `doc/convert/autoplay_stop_check.py`）

按帧建模（60Hz：1s = 60 帧，一次转场 73 帧，提交在第 35 帧），逐秒抽样
1~60s 按停止，逐条对齐 RTL（`fade_req` 保持型、FSM 只在 IDLE 采样请求电平、
预取延时可变）：

| 检查项 | 结果 |
|---|---|
| 队列积压可复现（排队 1/60 帧 > 消化 1/73 帧） | 通过（10s→3, 20s→5, 30s→6, 40s→7 饱和） |
| 改动前"停止后切图张数 == 存量 req_cnt" | 通过（10/20/30/40s 分别再多切 3/5/6/7 张） |
| 方案 B 后停止后剩余切换张数 ≤ 1 | 通过（1~60s 逐秒抽样最大值 = 1） |

## 17. 第十七轮：OSD 滚动字幕显示问题定位（仅定位，未改代码）（2026-10-05）

### 17.1 现象

黑字(纯黑)显示在红条(24'hFF0000, 100% 不透明)上;部分笔画缺几个像素;边缘有锯齿/断裂感;
字模 16x16。要求：不改字模数据，优先查坐标计算与采样逻辑。

### 17.2 结论速览

| 检查项 | 结论 |
|---|---|
| bit15 是否对应最左列 | **正确**。与 `python/font2verilog.py` 的 `bits |= 1 << (15-c)` 完全一致；若写反会有 990/3328 像素水平镜像 |
| row / col 索引偏移 | **无偏移**。全量 `scroll_pos` 0~831 × 640 列 × 16 行 = 1,966,080 点重采样，与字模逐像素 0 处不一致 |
| 坐标映射是否有非整数缩放 / 丢像素 | **无**。`dx` 恒为整数；12px 数字格与 16px 汉字格的列解码都精确(见 17.4) |
| 滚动 / 字符边界是否采样跳变 | **无跳变**。`SCROLL_PERIOD=832 = 192(串宽) + 640(轨宽)`，正好等于整串出屏；边界处沿用一个 `dx` 连续映射 |
| RGB 优先级 pixel_on > outline_on > background | **不存在该链**。`outline_on` 计算了但**悬空未接**(osd_engine.v L495 `.outline_on ()`)，只有 bg → 红条 → 黑字三级；文件头的"右下 2px 灰影"描述已与实现不符 |
| **字模基线(数字/字母 vs 汉字)** | **缺陷**：数字/字母只占 0~11 行(12 行)，汉字占 0~14 行(15 行)，两者都从第 0 行起画 → 屏幕上数字比汉字高 **3 px** |
| 字模数据空洞 | 66 px：其中 **14 px 是真断点**(横/竖笔画缺 1 px，如 '创' (3,6) 与 (6,9)(7,9)(8,9))，25 px 孤立针孔，**27 px 是两条笔画之间本来就该留的 1 px 缝** |

即：**"缺像素"不是采样丢的**，采样链与字模逐像素等价；真正的坐标缺陷只有一处(基线差 3 px)，
另有一处是字模数据自身的断点(可在采样侧补，不改数据)。

### 17.3 位序/索引的正确性证明（第 2、3、5 检查点）

- **位序**：`font_rom.v` 的 `pixel_on = fr_cur[15 - col]` ↔ `font2verilog.py` 的 `1 << (15-c)`，
  生成侧与 RTL 侧一致；模型反证：若改成 `fr_cur[col]`，13 套字模共 990 像素会水平镜像。
- **行序**：`fmt_verilog()` 把 `rows[0]` reverse 到最右一组，RTL 用
  `font_bits[{row, 4'b0} +: 16]` 取第 `row` 行 → 两侧一致，字形不倒置(见模型 A 段打印的 'F'/'P'/'6')。
- **列解码**：`c_col = dx[3:0] - c_xbase[3:0]` 用的是 4 位模运算，
  各位置 xbase 的 mod 16 值 = {0,12,8,4,0,12,8,4,0,0,0,0,0,0}，与 `dx` 在 12/16 宽格内的取值区间
  恰好对应，逐位置验证 col 结果均为 0~11 / 0~15，**没有取反、没有偏移、没有丢列**；
  `pos_of()` 的比较边界(12/24/…/176)与 `pos_xbase()` 完全一致，字符边界处不会取到相邻字模。
- **滚动**：`dx = pixel_x + scroll_pos - 640`，`scroll_pos` 每帧 +1(1 px/帧)，无小数步进；
  回绕点 832 时 `dx(pixel_x=0)=192=CELL_W` 刚好被门控挡掉，无缝。
  （注：`osd_engine.v` 头部注释里的 "336+640=976" 与 "0~687 循环" 是旧版残留，应以
  `SCROLL_PERIOD=832` 为准。）

### 17.4 唯一确凿的坐标缺陷：数字/字母基线差 3 px

实测 13 套字模包围盒(模型 A 段)：

| 字模 | 行范围 | 列范围 |
|---|---|---|
| '2' '0' '6' 'F' 'P' 'G' 'A'(12px 格) | **0~11** | 1~8 / 1~9 / 1~10 |
| '创' '新' '设' '计' '竞' '赛'(16px 格) | **0~13 或 0~14** | 1~15 |

两类字形都是"从字模格第 0 行开始画"，于是数字块比汉字块高 3 行：
屏幕上 `L1_Y0=462` → 数字底 473，汉字底 476 → **"2026FPGA" 比 "创新设计竞赛" 高 3 px**。
这正是"字符边界处看起来错位/断裂"的来源（采样本身不跳变，是字形基线跳了）。

### 17.5 最小修改方案（未实施，待确认）

**修复 1（坐标，推荐必做）**：给 12px 数字/字母格加 3 行垂直偏移，与汉字底边对齐。
改 `osd_engine.v` 的 `osd_text_cell` 三行（不动字模、不动其它模块）：

```verilog
// —— 现状 ——
wire [3:0]  c_col  = dx[3:0] - c_xbase[3:0];
wire [4:0]  c_row  = dy[4:0];
wire        f_zone = (dx < CELL_W) && (dy < 16'd16);

// —— 改为 ——
wire [3:0]  c_col  = dx[3:0] - c_xbase[3:0];
wire        c_digit = (c_sel < 4'd8);                       // 位置 0~7 = 12px 数字/字母格
wire [4:0]  c_row  = dy[4:0] + (c_digit ? 5'd3 : 5'd0);      // 下移 3 行, 底边与汉字对齐
wire        f_zone = (dx < CELL_W) && (c_digit ? (dy < 16'd13) : (dy < 16'd16));
```
- 数据范围校验：数字字模内容在 0~11 行，+3 → 3~14 行，**不越过 15 行**；
  门控把数字的 `dy` 收到 <13，避免 `c_row` 到 16/17 行读到相邻字模的数据。
- 屏幕上数字由 462~473 变为 465~476，与汉字底边 476 对齐，且仍在红条(460~479)内。

**修复 2（采样侧补缝，可选）**：只补"左右两侧都是笔画"的像素 = 上面 14 px 真断点。
`font_rom.v` 增加一个输出（复用已有的邻居切片，不加 ROM 数据）：

```verilog
output wire fill_on,     // 1 = 左右两侧都是笔画(1px 断点), 采样侧补缝用
...
assign fill_on = ~pixel_on & fr_cur[15 - c_left] & fr_cur[15 - c_right];
```
`osd_text_cell` 里接上并 OR 进字面：`assign face_on = f_zone && (f_px | f_fill);`
（`font_rom` 全工程仅 `osd_text_cell` 一处实例化，新增端口不影响别处。）

**明确不建议**：直接用现成的 `outline_on`（8 邻域）做膨胀 —— 新增 1102 px，
笔画出 2px 变 3~4px，并糊掉 4 套字模的内孔（如 '0' 的中孔）。
也**不要**补 27 px 平行缝（R1 规则），会把上下两条笔画粘成一条粗杠，字形变糊
（模型 F 段给出 '竞' 的 R1 / R3 对照图）。

### 17.6 关于"锯齿"

16x16 单色点阵 + `font2verilog.py` 的 `MinFilter(3)` 腐蚀 + LANCZOS 缩放 + `>128` 硬阈值
+ 倾斜剪切再阈值化 —— 斜笔画天然是阶梯，细笔画会被阈值削掉。这属于**字模生成链**的固有
产物，采样侧无法根治；要改善只能在生成端（提高灰度/换阈值/去掉剪切）或显示端加 1px 描边级。
另外注意：`font_rom.v` 里的 FONT_ALL **无法用当前 `font2verilog.py` 复现** ——
`render_char()` 有 `medium/erode` 参数，但 `main()` 没有暴露 `--medium`，也没有 13 字打包输出，
所以要重生成字库得先补工具；这也是建议在 RTL 侧修而不是重生成数据的原因之一。

### 19.2 为什么 +3 会裁掉顶部（第 18 节的方向搞反了）

设 `dy = pixel_y - L1_Y0`（L1_Y0 = 462），门控 `dy < 16` 决定了**只有 L1_Y0 及以下的行可见**：

- 修改前 `c_row = dy`：字模第 r 行显示在屏幕行 `L1_Y0 + r`，r = 0~15 全部可见；
- 修改后 `c_row = dy + 3`：字模第 r 行要显示在 `dy = r - 3`，即 **dy 必须 ≥ 3**；
  而 `dy` 从 0 开始 → **字模第 0、1、2 行永远取不到** → 数字/字母**顶部 3 行被裁掉**。

也就是说 `c_row = dy + 3` 的效果是**把字形整体上移 3 行**（不是下移），
顶部超出 `L1_Y0` 的部分被 `f_zone` 挡掉——与上板现象完全吻合。
参考模型 G 段已把这条作为反例固化：

```
[反例] c_row = dy+3 时, 数字/字母能采到的字模行 = 3~15,
       永远取不到的字模行(内容行 0~11 中) = [0, 1, 2] → 顶部被裁
```

**结论**：在做不到"给字符单独加行偏移"的前提下（`c_row` 必须 1:1 对应字模行），
数字/字母 12 行 vs 汉字 15 行造成的 3 px 高差**无法在采样侧消除**，
只能整体平移显示窗口。

|---|---|---|---|
| **462（现状）** | 462~473 | 462~476 | 汉字基本居中于红条(460~479)，3 px 高差保留 |
| 464 | 464~475 | 464~478 | 整体下移 2 px，3 px 高差保留 |
| 465 | 465~476 | 465~479 | 汉字底边贴到红条下沿，3 px 高差保留 |

只要不改字模数据，`L1_Y0` 平移会**同时移动数字和汉字**，高差恒为 3 px。

## 20. 第十八轮：字模生成算法重写（font2verilog.py 高分辨率渲染）（2026-10-05）

FPGA 侧一切不变（`osd_engine.v` / `top_tf_hdmi_audio.v` / 字符坐标 / 滚动逻辑 / RGB 优先级
全部未动，`font_rom.v` 的 RTL 结构与位序约定逐字保留）；本轮**只重写字体生成算法并重新生成
`font_rom.v` 的字模数据**。旧字模已备份为 `doc/convert/font_rom_before_regen_20261005.v`。

### 20.1 修改点（对照要求逐条）

| 要求 | 做法 |
|---|---|
| 1. 关闭 `MinFilter(3)` | **彻底删除**该调用。代码里只留 `ENABLE_ERODE = False` 开关，默认关；打开才会做腐蚀 |
| 2. 高分辨率渲染 | 16×16 只作最终目标：**128×128 工作画布 → 64px 字号灰度渲染 → 裁剪 → 等比缩放 → 贴回 64×64 → LANCZOS 缩到 16×16 → 阈值** |
| 3. LANCZOS | 全程显式用 `Image.Resampling.LANCZOS`（缩小与含裁剪缩放各一次）；**没有任何 NEAREST** |
| 4. 可调阈值 | `THRESHOLD = 110`（可 `--threshold 90/100/120` 快速试，**越小越粗**）；比较用 `> THRESHOLD` |
| 5. 关闭倾斜 | `ENABLE_ITALIC = False`，默认不做 shear；打开才会做（旧版的 shear+阈值就是锯齿/断笔的来源之一） |
| 6. 输出格式不变 | 仍输出 `localparam [3327:0] FONT_ALL = 3328'h...;`，右起第 1 组 = 编号 0 的 row0，bit15 = 最左列；`pos_to_font`、备用字库、解码逻辑逐字保留 → **可直接替换** |

新增/保留的可调旋钮：`FONT_WEIGHT`(可变字重 500)、`THRESHOLD`(**110**，见 20.8)、`ENABLE_ERODE`(False)、
`ENABLE_ITALIC`(False)、`DIGIT_BOX`(11×12)、`HAN_BOX`(15×15)、`LEFT_MARGIN`(1)。

**附带修掉的两个生成器自身缺陷**（本轮实测发现）：
1. 渲染画布太小：64px 字号的行框约 70+ px，直接画在 64×64 上会把字形底部（如 `'2'` 的底横）
   裁出画布 → 改为 128×128 工作画布再裁剪（这是新生成器必须的，否则 `'2'` 会显示成 `'7'`）。
2. 生成器不幂等：模板拼接处会每次多出一个空行 → 已归一化，连跑三次字节一致。

### 20.2 生成流程对比

```
旧: 16×16 画布直接渲染(字号16) → MinFilter(3) 腐蚀 1px → AFFINE 倾斜剪切(+1.2px) → 阈值>128
                                  ↑ 细笔画被吃掉        ↑ 斜线阶梯化            ↑ 灰度边缘被丢弃

新: 128 画布/64px 灰度渲染 → 裁剪 → 等比缩放到排版盒(数字 11×12 / 汉字 15×15)
    → 贴回 64×64(1px 左边距, 顶对齐) → LANCZOS 缩到 16×16 → 阈值>100
       ↑ 无腐蚀            ↑ 无倾斜                ↑ 用灰度覆盖率定二值, 边缘平滑
```

### 20.3 为什么能改善锯齿/断笔（原理）

1. **斜线直方图化**：旧版 16×16 直接渲染时斜边只有"整格开/关"两种状态，再叠加
   1.2 px 剪切 + 硬阈值 → 阶梯断续。新版在 64×64 上渲染、再 LANCZOS 缩到 16×16，
   每个目标像素是 4×4 源像素的**加权平均覆盖率**，斜边得到亚像素级的"台阶均分"，
   阶梯更均匀、不再断裂。
2. **笔画不再被腐蚀**：旧版 `MinFilter(3)` 把笔画外缘整体剥掉 1 像素，16 px 字面下
   1 px 就是 1/12 字高，细横竖直接被抹掉 → 表现为"缺像素/断笔"。新版无腐蚀，
   笔画完整。
3. **不再丢灰度信息**：旧版先二值化 32×32 再 LANCZOS（等于先丢灰度再缩放，产生
   半灰度伪影），新版是**先灰度缩放、最后一步才二值化**，信息损失最小。
4. **无倾斜剪切**：`AFFINE` + 阈值会在斜笔画上造成 1 px 错位与孤立像素，本版默认关闭。
5. **不做膨胀**：只靠阈值"保留"像素，不做任何 dilation / 8 邻域填充，所以空心字内孔、
   笔画之间的 1 px 缝不会被糊死（对比表里"内孔"列可验证）。

### 22.2 关键设计点

1. **切缓冲为什么不增加 SDRAM 带宽**：`frame_fifo_read` 每帧在 `read_req`（vs 边沿）都会
   `fifo_aclr` 清 FIFO 并整帧重读，切缓冲只是换 `read_addr_index` 的基址，
   **不会产生额外读请求**。切缓冲那一帧整屏全黑，把 CDC(2 拍) + `S_ACK`/清 FIFO +
   首批像素预取的延迟全部盖住。
2. **握手完全复用**：`fade_start`(保持型请求) 与 `fade_done`(整黑帧脉冲) 两个 wire 被
   淡化与黑幕共用；sd_card_bmp 侧的 `fade_req / fade_pending / fade_wait_cnt / fade_timeout /
   req_cnt / pfb_valid / disp_buf_idx / img_idx / 提交块` 一行未改。
3. **只作用于底图**：黑幕 MUX 插在 `bg_eff`（红条 L0 与黑字 L1 之前），
   所以"底图 → 黑幕 → 红条 → 黑字 → output"的层次天然成立，OSD 不受影响。
4. **无乘法**：`scale_by_alpha` 的两处 alpha 缩放在 mode10 下 `alpha=255` 直通不生效；
   新增 datapath 只有 `pixel_x[9:0] < wipe_pos` 一个比较器 + 一个 24bit MUX。
5. **无行内撕裂**：`wipe_pos` 只在 `vs_fall` 更新，整帧内是常量。
6. **模式中途变化的处理**：黑幕过程中把 sw 拨离 `2'b10` 时，先补一个 `fade_done` 脉冲
   再回 `W_IDLE`，否则 `sd_card_bmp` 的 `fade_pending` 会挂到 5s 超时（表现为"卡 5 秒才跳图"）。

### 22.3 参数（全部是 localparam，便于再调）

| 参数 | 取值 | 说明 |
|---|---|---|
| `WIPE_W` | 640 | 屏宽 |
| `WIPE_STEP` | 16 px/帧 | 40 帧/阶段；**不得 < 8**，否则总时长会超过 5s 超时 |
| `W_SWITCH_HOLD` | 4 帧 | 整黑等待，覆盖切缓冲 + FIFO 重填 |
| `WIPE_HOLD_F` | 2 帧 | 揭开后收尾 |

### 22.4 四种模式的最终行为

| mode | 数码管(第7位 sw1 / 第6位 sw2) | sd_card_bmp 路径 | osd_engine 行为 |
|---|---|---|---|
| `2'b00` 硬切 | 0 / 0 | 路径 B：立即翻转缓冲 | 两个 FSM 都不动，直通 |
| `2'b01` 淡入淡出 | 1 / 0 | 路径 A：保持型请求 + 整黑帧脉冲 | 两段式 alpha（**逻辑逐位未改**，只加了 mode 门控） |
| `2'b10` 横向黑幕 | 0 / 1 | 路径 A：同一套握手 | 黑幕 FSM（新增） |
| `2'b11` 预留 | 1 / 1 | 路径 B：等同硬切 | 都不动 |

### 22.7 已知边界情况

- 淡化进行中把 sw 拨到 `2'b10`：淡化 FSM 会因 `mode_fade` 变假而中止并发 done（等效硬切），
  随后残留的请求电平可能让黑幕 FSM 紧接着跑一轮（在已经切好的图上再擦一次）。
  发生概率低（要在 1.2s 淡化窗口内拨开关），如需彻底避免可在黑幕入口加"刚收到 done 后的 1 帧锁存"。
- `W_SWITCH_HOLD=4` 是按"切缓冲延迟 + FIFO 重填"估的保守值；若上板看到揭开瞬间左上角
  有旧图残影，把它加到 6 即可（总时长仍在 5s 内）。

### 22.8 上板复核要点

- SW1 下 / SW2 上 → 按 key1（或自动轮播）：应看到黑幕从左向右盖住旧图 → 整黑一瞬间换图 →
  黑幕从右向左退开露出新图；数码管第 4 位应出现 `4→5→6→7→8→0` 的序列；
- 红条与黑字字幕在转场全程保持常亮、不被压暗（第 4 位显示 5 和 7 时最明显）；
- SW1 上 / SW2 下（淡入淡出）应与改动前完全一致（回归验证点）；
- SW1 下 / SW2 下、SW1 上 / SW2 上 应分别是硬切，第 4 位恒为 0。

### 22.9 综合报错修复：`port 'seg_data_2' is already connected`（2026-10-05）

**现象**：综合报 `HDI-8007: port 'seg_data_2' is already connected (top_tf_hdmi_audio.v:300)`。

**根因**：上一轮把数码管第 4 位改成状态码时，我的编辑在插入 `.seg_data_1` 行之后
**又多写了一行 `.seg_data_2`**，而下方本来就已有一行 `.seg_data_2`（第 5 位空白），
于是同一个实例里 `.seg_data_2` 出现两次。括号与 `begin/end` 全部配平，
所以 `vstruct_check.py` 当时没报出来，是综合器第一个发现的。

**修复**：删掉重复的那一行，`seg_scan` 六个数据端口恢复"各一次"。

```diff
     .seg_data_0        ({1'b1,7'b1111_111}),    // 第3位: 空白(未使用)
     .seg_data_1        ({1'b1,trans_state_seg}),// 第4位(E10): 转场/黑幕状态码
     .seg_data_2        ({1'b1,7'b1111_111}),    // 第5位: 空白(未使用)
-    .seg_data_2        ({1'b1,7'b1111_111}),    // 第5位: 空白(未使用)
     .seg_data_3        ({1'b1,seg_sw2}),        // 第6位(F10): sw2 状态
     .seg_data_4        ({1'b1,seg_sw1}),        // 第7位(E11): sw1 状态
     .seg_data_5        ({1'b1,seg_data_0})      // 第8位: state_code 诊断(未改动)
```
