## 1. 板级与硬件

### 1.1 按键丝印搞反了

**现象**：让用户"按 KEY1 切图"，用户按了没反应，或者系统重新初始化要等 6 秒，被误判为"按键失效/卡死"。

**根因**：板上丝印和逻辑命名对不上。

| 板上丝印 | FPGA 引脚 | 实际功能 |
|---|---|---|
| KEY1 | A2 | **复位** |
| KEY02 | B2 | **切图**（代码里叫 `key1`） |
| KEY04 | C1 | **轮播**（代码里叫 `key2`） |

代码里的 `key1`/`key2` 指的是**丝印 KEY02/KEY04**，不是丝印 KEY1。

**教训**：涉及板级操作前，先查引脚/丝印对照表。这个问题在 MEMORY.md 里记过，但没查，直接导致用户反复按复位、每次都触发重新初始化（约 6 秒无响应），被当成 bug 追了一轮。

## 2. 宏定义与 Verilog 表达式

### 2.1 Verilog 乘法位宽陷阱

**现象**：整屏全黑，频谱一根柱子都不出来。

**根因**：

```verilog
reg [7:0] c, k;
wire [7:0] dim = (c * k) >> 8;   // 恒为 0！
```

两个 8 位操作数相乘，**结果位宽仍是 8 位**（不是 16 位）。乘积在赋值前就被截断了，再右移 8 位必然是 0。

**解法**：

```verilog
reg  [15:0] p;
always @(posedge clk) p <= c * k;
wire [7:0] dim = p[15:8];
```

**教训**：Verilog 里表达式的位宽由**操作数最大位宽**决定，不是由结果需求决定。乘法和移位必须显式扩位。

### 2.2 宏定义缺括号

**现象**：SDRAM 完全零刷新，空闲 20~30 秒后切图出现彩色噪点。

**根因**：`include/global_def.v` 里

```verilog
`define SDR_CLK_PERIOD  1000000000/125000000     // 少了括号
`define SELF_REFRESH_INTERVAL  (64000000/`SDR_CLK_PERIOD/2048)
```

展开后变成 `64000000/1000000000/125000000/2048`，从左到右依次整除，**结果是 0**。于是：

- `init_cnt` 冻结在 0
- `ref_req` 永远不产生
- `App_ref_req` 恒 0
- → 全机零刷新

**解法**：宏里凡是复合表达式都加括号。

```verilog
`define SDR_CLK_PERIOD  (1000000000/125000000)
```

修复后 `SELF_REFRESH_INTERVAL = 3906` 拍 = 31.248us（2048 次/64ms，符合 JEDEC 11 位行地址标准）。

**教训**：宏是文本替换，不是函数。任何含运算符的宏定义都必须整体加括号。这类 bug 仿真时如果不检查宏展开值，根本看不出来。

### 2.3 点阵常量的位切片方向（`+:` 往高位取）

**现象**：屏幕上的时间戳上下颠倒，每个数字都翻了个个儿。

**根因**：

```verilog
wire [15:0] glyph_row = glyph_bits[{tdy[3:0], 4'b0} +: 16];
```

生成点阵常量时，是"row0 写在最高位、row15 写在最低位"（按文本从上到下顺序累加）。
但 `[base +: width]` 是**从 base 向高位取 16 位**。`tdy=0` 时 base=0，取到的是 `bit15..0`
——正是**最后一行**。于是 `tdy=0` 显示的是 row15，整个字形上下颠倒。

**解法**：索引前先反序行号。

```verilog
wire [3:0]  row_idx   = 4'd15 - tdy[3:0];
wire [15:0] glyph_row = glyph_bits[{row_idx, 4'b0} +: 16];
```

**教训**：`[base +: width]` 的方向和"文本从上往下写"的直觉相反。凡按行存储的常量，
索引都要先反序。**左右方向不用翻**（`[15 - col]` 那种逐位取是另一回事）。

## 3. 按键与请求链路

这一组是"按键不切图"的完整根因，四条叠加（2026-10-31）：

### 3.1 按键请求全部失效

**现象**：OSD 文字、状态条都正常变化，但图片就是不切换。

**根因（四条叠加）**：

1. **加载请求是单拍脉冲**。`bmp_read` 停在 `ST_SCAN` 读扇区（一次要几百 us），单拍脉冲必然被漏掉 → 预取不执行 → `pfb_valid` 恒 0。
2. **续扫也是一次性脉冲**，被 `ST_LOAD_DATA` 尾部吃掉后永久停扫 → `scan_done` 恒 0。
3. **`ST_SCAN` 无超时**，遇到坏/慢扇区永久挂死。
4. **收敛判据只要 1 张**就收尾 → `img_found_count == 1`，自动轮播和换图都失效。

而 `key/auto/prefetch` 全部用 `scan_done` 硬门控，`scan_done` 又是 0，所以按键全失效。OSD 只看 `sw1/sw2`，所以文字能变——造成"按键有反应但图不动"的假象。

**解法**：

- 单拍脉冲 → **保持型电平** `load_req`，撤销条件 `load_req_taken = load_req && bmp_ready && !scan_start_pulse`
- 新增 `scan_resume_req` 电平续扫 + `bmp_read` 输出 `scan_paused_o`
- `ST_SCAN` 加单扇区超时 `SCAN_SECTOR_WAIT_MAX = 20'hF_FFFF`（≈10.5ms）
- 收敛判据改为 `scan_found_total >= 2`
- 三条请求路径去掉 `scan_done` 硬门控
- `source_started_seen`/`source_done_seen` 加 `!load_req` 守卫（电平化后 `load_complete` 会提前触发导致撕裂）

**教训**：**跨模块握手不要用单拍脉冲**。当接收方可能处于长时间阻塞状态时，脉冲必丢。用"电平 + 显式撤销"是唯一可靠的做法。

### 3.2 保鲜重写抢显示缓冲

**现象**：快速连按几次后，画面永远不动，按什么都没反应。

**根因**：`sd_card_bmp.v` 的 5 秒保鲜重写分支只查 `!load_busy`，不查 `!fade_pending` / `req_cnt`。它和切图提交都用同一个旧 `disp_buf_idx` 算目标缓冲（重写写 `disp^1`，提交把 disp 翻成 `disp^1`）。两者同拍时，重写写进了刚变成显示的缓冲，完成后 `pfb_idx == img_idx` → 之后每次按键只翻缓冲、`img_idx` 不变 → 画面永远不动。

快按时系统几乎全程在转场中（一次 1.27s），撞车概率被大幅放大。

**解法**：重写条件补全

```verilog
&& !fade_pending && !mode11_pending && (req_cnt == 3'd0)
```

**教训**：**只要"完全空闲"才允许做后台维护操作**。条件不完整时，后台任务会和前台请求抢同一份资源，而且这种 bug 只在高频操作下才出现，平时测不出来。

### 3.3 请求队列只有 2 级

**现象**：快按第 3 下之后，请求被静默丢弃。

**解法**：`REQ_QUEUE_MAX` 2 → 4（`req_cnt` 是 3 位，最大 7，4 级在位宽范围内）。

**顺带**：`req_queue_clear` 的条件比切换条件宽松，导致"切换被拒但仍清空队列"。已补全成与切换条件完全一致。

### 3.4 数码管诊断位（很有用，别再重新发明）

| 物理位 | 信号 | 含义 |
|---|---|---|
| 第 3 位 | `req_cnt` | 0=按键没进队列，1~4=有请求排队 |
| 第 5 位 | `{fade_pending, pfb_valid}` | 0=空闲但缓冲未就绪(异常) / 1=正常待机 / 2=转场中 / 3=转场中且缓冲就绪 |
| 第 8 位 | `state_code` | 来自 `bmp_read.v`：0=未初始化或加载超时，1=IDLE，2=扫描/读头，3=等写，4=读数据 |

**注意**：`state_code` 是 `bmp_read.v` 的输出，**不是 SD 状态机**。查错时别找错地方。

## 4. SDRAM 刷新

### 4.1 SDRAM 零刷新的元凶（宏定义缺括号）

见 [2.2](#22-宏定义缺括号)。

**关键判别实验**：空闲 30 秒后切图出现花屏，**立刻再切一次就干净了** → 单缓冲电荷泄漏模型成立，可以排除写通道/仲裁/时序类原因。这个实验设计值得记住：用"再切一次是否恢复"来区分"数据损坏"和"逻辑卡死"。

### 4.2 开刷新出现彩色条

**现象**：修好刷新后，每张图都有彩色小条**持续**闪动（和空闲无关）。

**根因**：该 SDRAM 控制器的 **REF 仲裁路径从未被验证过**。REF 插入读突发导致返回数据延迟或错位。

**结论**：这条路径整体不可用，不要试图调参数救它。

### 4.3 慢刷新仍然挂死

**尝试**：降到 64 倍慢刷新（每 2ms 刷一行，全片 4.1 秒扫一遍）。

**结果**：只能切一张图，之后按键全无响应 → REF 和写突发相撞把仲裁挂死。

### 4.4 最终方案：关硬件刷新 + 保鲜重写

**做法**：

- `sdram.v` 的 `self_refresh_open` 设为 `1'b0`（关硬件刷新）
- `sd_card_bmp.v` 每 5 秒把备用缓冲里同一张图**从 TF 卡原样重读、写回同一块缓冲**

**为什么可行**：

- 读操作本身会刷新该行 → **显示缓冲天然安全**，不需要额外刷新
- 备用缓冲长期不被访问会电荷泄漏 → 定期重写保鲜
- 重写内容与原内容完全一致，屏幕无感知
- 走的是已验证的写通道，不引入新的时序交互

**参数选择**：5 秒相对实测 20~30 秒保持时间留了 4~6 倍余量。

**教训**：当一个硬件特性（刷新）无法可靠工作时，绕开它比修它更划算——前提是能找到等效的替代路径（这里是"读操作自带刷新"这个物理事实）。

## 5. 时序与布线

### 5.1 bars[] 组合读导致局部拥塞

**现象**：布线报错

```
PHY-8023 ERROR: Location: (x18y64_e2beg4)
  nets: u_spectrum_engine/mux140_syn_2[639]  mux140_syn_2[623]
RUN-8102 ERROR: Incremental route failed.
```

**根因**：`spectrum_engine.v` 里 `bars[0:79]` 是**组合读**（`bar_h = bars[bar_idx_s]`）。综合把它实现成一个 640 位大 mux（约 320 个 LUT），全部集中在一处，把局部走线挤爆。

**关键**：整体密度只有 43~50%，这是**局部拥塞**，不是资源不足。所以看整体利用率没用。

**解法**：换 seed（见下表）。根治方法是改成同步读走 RAM。

### 5.2 布线器崩溃

**现象**：TD 在 `opt_route` 阶段访问违例崩溃（`0xC0000005`），综合和布局都正常通过。

**根因**：TD 6.2.168116 的已知 bug。A/B 隔离实验证明：修复版（3885 slices）3/3 崩，回退版（3833 slices）稳定通过 → **只多了约 50 个 slice 就触发**。

**解法**：`D:/TD/doc/scripts/DefaultFlow.tcl` 顶部加 opt-in 守卫：

```tcl
if { ![info exists phyWildParams] && [file isfile .use_seed2] } {
  set phyWildParams {place seed 8 place effort high route effort high}
}
```

运行目录存在 `.use_seed2` 标记文件时，才启用 place seed + 高 effort。

**坑中坑**：TD 每次运行会重写 `settings.cfg`/`run.bat`，往那里追加参数会被冲掉。必须写在 `DefaultFlow.tcl` 里。

**注意**：TD 里 Clean 或删运行目录会丢 `.use_seed2` 标记，需要重建。

### 5.3 seed 对时序的影响极大

同一网表，不同 seed 的 Setup WNS 波动可达 ±400ps：

| seed | 结果 |
|---|---|
| 2 | 布不通（PHY-8023 拥塞） |
| 3 | 布通但 Setup −425ps / 6 违例 |
| 5 | Setup +128ps / Hold +11ps / 0 违例 ✓ |
| 6 | Setup −800ps / 4 违例 |
| 7 | Setup +119ps / Hold +3ps |
| 8 | Setup +156ps / Hold +11ps ✓ |

**但 Hold WNS 基本是设计固有的**：seed 6/7 都是 +3ps，换 seed 几乎不变。所以 **Hold 不达标时不要浪费时间去遍历 seed**，要从设计上解决（缩短关键路径/加流水）。

**工具**：`verification/spectrum_mvp_20261101/build_retry.py` 自动遍历 seed，判据是"有 bit + 无路由错误 + Setup/Hold WNS ≥ 0 + 0 违例端点"。

```bash
python build_retry.py                    # 默认 7,6,8,9,5,3,10,11
python build_retry.py --seeds 7 --min-hold 10
```

**注意**：同一 turn 内连续删文件过多会触发安全钩子（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`）中断脚本，此时 bit 已被删、seed 停在半路，用 `--seeds N` 单跑一次即可恢复。

## 6. TD 工具链

### 6.1 TD 命令行卡在 `td >` 提示符

**现象**：`td_commands_prompt.exe` 跑完不退出，进程挂死（最长挂过 7 分钟）。

**根因**：遇到错误后进入交互模式等待输入。

**解法**：必须重定向 stdin。

```bash
td_commands_prompt.exe D:/TD/doc/scripts/DefaultFlow.tcl < /dev/null
```

**另一个坑**：运行目录里必须同时有 `settings.cfg` **和** `HDMI1.4b_Transmitter_v1.0.prj`，只放 `settings.cfg` 会报 `PRJ-8642`。

### 6.2 TD 解析器不支持 case 合并项

**现象**：

```
HDL-7279 CRITICAL-WARNING: illegal empty item in case item list
HDL-8007 ERROR: syntax error near 'default'
HDL-8007 ERROR: Verilog 2000 keyword 'default' used in incorrect context
```

**根因**：写了 `S_ERR, default:` 想合并两个分支。标准 Verilog 允许，但 TD 的解析器不认，把 `S_ERR,` 当成空项。

**解法**：拆成两个独立分支（代码重复但安全）。

**教训**：**换工具链时不要用"标准允许但少见"的语法**。合并 case 项、`always_comb`、`logic` 等，在这个工具链上都有风险。

### 6.3 综合/布线的分工

| 步骤 | 目录 | settings.cfg | 说明 |
|---|---|---|---|
| 综合 | `src/td_probe` | `start_step=read_design` `end_step=opt_gate` | 约 30 秒 |
| 布线 | `src/td_phy` | `start_step=opt_place` `end_step=bitgen` | 约 70 秒/seed |

```bash
cd src/td_probe && td_commands_prompt.exe D:/TD/doc/scripts/DefaultFlow.tcl < /dev/null
cd verification/spectrum_mvp_20261101 && python build_retry.py --seeds 7
```

**重要**：`opt_gate` 阶段的 WNS 是**未布局估算，没有参考价值**（实测 r10 综合 −1182ps、布线后 +340ps）。只看布线后的数。

### 6.4 ModelSim 的坑

- `vsim` 10.1d 不支持 `-nolog`；并行时靠"每任务独立 cwd"隔离 `transcript`/`wlf`
- `vlog` 用 `+define+NAME`，不是 `-define+`
- SystemVerilog 模式下模块级 `integer` 必须**先声明后使用**（否则 `vlog-2730`）
- 函数内不能有 `@(negedge clk)`，有界等待要写成 task + 全局标志
- `$display` 里的中文在 GBK 控制台会变 `?`，日志一律用 ASCII

## 7. 判断"改没改"的判据

### 7.1 看寄存器数，不要看 LUT

**判断代码改动是否真的生效，看 `seq`（寄存器数）。**

TD 综合报告的 `Report Hierarchy Area` 有逐实例数据。LUT 会在模块边界之间漂移——实测没碰过的 `bmp_read_m0` 也会 +26。

**寄存器数不变 = 逻辑结构没变**。这是最可靠的判据。

### 7.2 bit 文件不能按字节差异判断改动大小

bit 是压缩流，布局一动，46% 的字节就不同。改一行和改一百行，字节差异可能一样大。

### 7.3 同源码 + 同 seed 是确定性的

631952 字节里只有偏移 139-140（2 字节时间戳）不同。这个特性可以用来验证"这次构建和上次是不是同一个东西"。

### 7.4 点阵/查表逻辑用"扫坐标打 ASCII"验证

时间戳字形颠倒那次，没有靠猜，而是写了个 ModelSim tb 做像素级反查：

1. `force` 内部寄存器到已知状态（例如时/分/秒 = 12:34:56）
2. 逐像素扫过显示区域，把"该像素点亮"打成 `#`、否则打成 `.`
3. 输出直接就是一张 ASCII 图，和源字形逐位对照

```verilog
for (y = 28; y < 44; y = y + 1) begin
    for (x = 12; x < 140; x = x + 1) begin
        #1;
        $write((hit && (pix == TEXT_COLOR)) ? "#" : ".");
    end
    $write("\n");
end
```

一眼就能看出 `1` 的底座跑到了最上面。

**这套方法适用于任何纯组合的点阵/查表/坐标命中逻辑**，比烧到板子上看快得多，
也比肉眼盯屏幕准。

ModelSim 跑法（10.1d）：

## 8. 返工复盘：为什么让你重烧了这么多次

这一节是给 AI 自己看的。用户 2026-11-01 明确提出："好好反省一下为什么让我修改这么多次"。

### 8.1 一次改多处，无法二分定位（最严重的错误）

r11 我在一个版本里塞了 **4 处改动**：

1. SPI 降速 25MHz → 12.5MHz
2. `S_WAIT_READ_WRITE` 跟随参数
3. `S_IDLE` 加 200ms 上电等待
4. 补 `S_ERR` 分支 + `default` 清握手信号

结果用户烧完全不能切图。这时**无法判断是哪一处的问题**，只能整体撤回再逐个加，白白多一轮烧录。

如果当时只改第 1+2 处（降速），一次就成了。

**正确做法**：诊断阶段一次只改**一个**变量。加固项要分开做，一个一个上板确认。

### 8.2 没有先确认基线

MEMORY.md 规则第 1 条写着"**改动前先确认基线功能完好**"，是我自己写的，自己没执行。

正确流程应该是：

1. 先让用户把当前可用的 bit 烧回去，确认"能切一张然后卡死"的现象还在
2. 确认基线正常后，再上改动

这一步能排除"根本不是代码问题"（TF 卡接触、卡里文件、供电），省掉大量瞎猜。

### 8.3 200ms 阻塞等待是本次返工的主因

**我的推理**：SD 卡规格要求上电后等待，原设计只发了 88 个 0xFF 时钟（200kHz 下约 440us），不足 1ms，所以加 200ms 更稳妥。

**错在哪里**：我只考虑了"上电时等一等有好处"，**没考虑 `rst` 的动态行为**。

```
rst_all = ~rst_n | ~audio_pll_lock
```

`rst_all` 同时复位 SD 控制器、`bmp_read`、`sd_card_bmp`。只要音频 PLL 的 `lock` 有抖动，整套 SD 链路就被踢回 `S_IDLE`。

- r10（原来）：`S_IDLE` 立刻进 `S_CMD0`，几毫秒就重新初始化完，用户感知不到
- r11（我改的）：每次都要重等 200ms，抖动间隔比这短就**永远爬不出来**

结果就是完全初始化不了、一张都切不动。

**这是典型的"加固反而引入新故障"**：加分支时只想着正常路径，没想异常路径的交互。

**教训**：
- 任何**阻塞/延时**逻辑，先问"这条路径会被谁反复触发"
- 先确认 `rst` 的稳定性，再决定要不要在里面加等待
- "更稳妥"的直觉在嵌入式里经常是错的

### 8.4 定位错模块

我一开始把数码管第 8 位 `state_code` 当成 `sd_card_sec_read_write.v` 的状态机输出来分析，实际它来自 `bmp_read.v`。差点在错误的文件里改半天。

**教训**：debug 信号先追到**定义处**，不要凭名字猜。

### 8.5 想当然的判断（历史案例）

- r4：我判断"上电初期柱高为 0 所以不显示"，用户实测发现频谱柱先出现。**错了**，FFT 只要有音频就开始出柱高（约 21ms 一帧），比 SD 卡加载首图快得多。
- r8：柱高压缩我放进了 `spectrum_engine.v`，导致 `bars[]` 语义变化，必须同步改 `BAR_TOP`、明度截距、`gen_stim.py` 三处。到 r10 又把它挪回 `spectrum_overlay.v`——**同一个需求做了两遍**。

**教训**：改之前先问"这个改动的最小作用域在哪"，优先改下游/绘制端，不要动数据通路的语义。

## 9. 以后的做法（硬性约束）

1. **一次只改一个变量。** 诊断阶段尤其严格。加固项分开交付，一个一个验证。
2. **改动前先确认基线。** 先让用户烧回上一个可用版本，确认现象复现，再动手。
3. **改动前说清风险。** 这次要重建、要重烧、可能影响哪些功能，先讲明白。
4. **纯视觉参数只动绘制端**（`spectrum_overlay.v`），不碰数据通路语义。
5. **交付前确认没有并发构建；交付后不再动构建目录。**
6. **每次交付附上板检查清单**：上电首图 / 按键切图 / 连续切多张 / 静置后切图 / 转场（黑幕+淡入淡出）/ OSD 字幕与状态条 / 频谱。
7. **不确定就先问。** 尤其是板级操作、烧录方式、现象细节（有没有画面、按键有没有反应），问清楚比猜快得多。
